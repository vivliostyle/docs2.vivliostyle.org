> 注記（2026-11-06）：以下の表にある「コミット作成：私の判断（開発の段階に応じて）」は旧規則の記録である。現行の規則は全体指示および `.agents/memory/commit-approval-current-rule.md` にあり、コミットを含むGitの状態変更操作の前には説明と明示的な承諾が必要である。

開発フローのチェックポイント：

| 段階 | 必要な確認 |
|---|---|
| **作業開始前**（コード変更、実装着手、PR/issue/コメントの投稿、外部システム操作 等の実体変化に着手する前） | ユーザーへの **説明と許諾必須** |
| **コミット作成** | 私の判断（開発の段階に応じて） |
| **push 前**（origin/外部リポジトリへの push） | ユーザーの **承認必須** |
| **PR/issue へのコメント・返信投稿前** | ユーザーの **承認必須**（GitHub 上に出てしまうと取り消しに edit/delete 操作が必要なため、push と同じ扱い）|

**Why:**

- 1 回目：dark-mode CSS 削除を説明なしで実装。ユーザーから「変更する際は、必ずユーザーへの説明と承認が必要です」「控えめに言って不愉快です」と明確な指摘
- 2 回目：村上さん（@MurakamiShinyu）からのレビュー指摘に対して、修正適用 → コミット → push → インライン返信投稿、までフルパスで進めた。ユーザーは「対処をお願いします」と言ったが、それは具体内容と返信文案を見せて承認を取るプロセスを省略してよいという意味ではなかった。「これを言うのは初めてではないはずです」と再指摘を受ける
- 3 回目：docs2.vivliostyle.org #57（AIポリシーPR）で、直前に「確認質問で仕事を増やすな」という別のフィードバック（[[feedback_decide_dont_ask]]）を受けたのを、このpush承認ルールにまで拡大解釈してしまい、CLAUDE.mdシンボリックリンクの追加、`.gitignore`へのaiderローカル状態追加という2件のコミットを、承認なしに連続してpushした。ユーザーから「実装にとりかかる前に、必ずユーザーの確認、承認を得てください。あなたのその行動こそが、本PRのようなルールが必要であることを証明しています」と指摘された。皮肉にも、これはAI生成物を人間がレビューしてからマージするという、まさにそのPRで書いていたAI_POLICY.md自体の原則への違反だった。

**How to apply:**

- **[[feedback_decide_dont_ask]] とは独立した別のルールである。** 「判断・選択を自分で決めてよい」という許可は、「pushしてよい」「GitHubに投稿してよい」という許可を一切含まない。ambiguateな要件をどう解釈するかは自分で決めてよいが、その結果を外部に公開する行為そのものは、その判断の確からしさに関わらず、常に別途の承認が要る

- auto mode が active であっても、「reasonable assumption」と称して変更を先行させない
- ユーザーから「対処をお願いします」「対応して」のような **方向性の承認** を得ても、それは具体的な diff・文案・コミットメッセージへの承認ではない。**作業開始前に具体案を必ず示す**
- 例外的に省略できるのは、「proposal 1〜5 を実行しましょう」のように **ユーザーが明示的に各 proposal の中身を確認したうえで一括承認した場合** のみ
- diff や文案を提示するときは「これでよろしいですか？」と明示的に承認を求めるフレーズを必ず添える
- push 前と GitHub 投稿前は、たとえコミット内容を事前に承認済みでも、**push/投稿のタイミング自体** にも承認が必要（ユーザーが「これは後でまとめて push する」「先に確認したい」等の判断をする余地を残す）
