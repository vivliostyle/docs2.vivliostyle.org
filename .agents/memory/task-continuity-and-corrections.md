# 作業を完了まで継続し、指摘後は修正する

記録日: 2026-10-30

## 起きたこと

上流サブモジュールの更新作業で、更新、ブランチ作成、コミット、PR 作成をそれぞれ作業完了のように扱い、ユーザーが継続を求めるたびに応答を終えてしまった。また、README の未変更を指摘されたとき、対象を確認して修正に進まず、説明だけで終えた。

## 次回の対応

- 複数段階の依頼では、最初のユーザー依頼を完了条件として保持し、ブランチ作成、コミット、PR 作成、レビュー待ちを途中の工程として扱う。
- 依頼の目的から成果物の全体像を先に洗い出す。上流リポジトリの更新では、サブモジュールの同期だけでなく、詳細な日英変更履歴、トップページの日英変更履歴要約、PR の説明を確認し、更新対象として列挙する。対象の呼び方（例: README）が実際のどのファイル／ページを指すか曖昧なら、リポジトリ内で該当箇所を検索してから編集対象を決める。
- 作業完了前に、列挙した各成果物を個別に照合する。「変更履歴ページを更新した」ことを「トップページの変更履歴も更新した」ことの代わりにしない。
- 最終応答の前に、依頼された成果、実施済みの作業、未完了の作業、ユーザー側の操作待ちを照合する。未完了項目があれば、単に状況を報告して終えず、許可された作業を続ける。
- ユーザーの指摘や訂正は、元の目的に対するステアリングとして扱う。まず省略した作業や誤った前提を特定し、指摘を認めるだけで終わらず、修正して結果を検証する。
- 操作に個別の承諾が必要な場合は、その操作の説明と確認を行う前に、依存しない調査・準備・レビューを済ませる。承諾を得たら、同じ目的に戻って実行と確認を続ける。
- 外部認証やユーザー操作が本当に必要な場合だけ、その具体的なブロッカーとユーザーが行う操作を明示する。認証待ちを理由に、認証後の push や PR 作成など承諾済みの後続作業を忘れない。
