技術記事の執筆では、**まずコードで動作確認 → 確認した内容だけを書く** を厳守する。
推測・伝聞・「動くはず」での記述は禁止。

**Why:** ユーザーが「PRでこのような書き直しをしなければならなくなったのは、これを怠ったためです」と明言した。
前回のPR (responsive-images.md の CMYK/TIFF 例) では、Vivliostyle (Chromium) が TIFF を描画しない・CMYK を保持しないという基本事実を確認せずに書かれた結果、レビュアー (Shinyu) から「例が成立していない」と指摘され、記事全体の見直しが必要になった。
記事のレビュー指摘の大半は「書く前に動かしていれば気づけたこと」であり、これは執筆コストではなく検証コストの欠如が原因。

**How to apply:**
- 機能を紹介する記事を書く前に、**そのコードを実際に書いて動かす**。PDF/HTML/EPUB 等、想定する出力で確認する。
- 「期待通り動かなかった」「想定外の制約があった」場合、記事の構成・例自体を変える判断をする。動かない例を「動く」と書かない。
- 既知の制約（例: vivliostyle-cli #811 で EPUB に source srcset が同梱されない）は、それを踏まえて記事の趣旨を再検討する。
- 検証スクリプト・テストファイルは記事と一緒にコミット候補としておくと、後のメンテナンスにも役立つ。
- ユーザーが書いた既存原稿を整理・書き換える場合も同様。「元原稿にそう書いてあるから」を根拠にしない。
